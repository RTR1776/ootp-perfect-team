# Stack recommendation — OOTP PT Optimizer

You asked for: deploys to Vercel, fast/snappy, really nice UI, room for a ton of data, possibly productize. Here's the stack I'd build on and why.

## The stack

**Framework**
- **Next.js 15** (App Router) + **TypeScript**. Owned by Vercel — zero-config deploy, edge runtime, RSC for fast first paint. The path of least resistance for everything you said you wanted.

**UI**
- **shadcn/ui** + **Tailwind v4** + **Radix primitives**. The current "really nice UI" defaults. Copy-paste components you own (no opaque npm dependency), accessible by default, looks professional out of the box.
- **Framer Motion** for transitions. Use it sparingly — the polish-per-line-of-code is enormous.
- **lucide-react** for icons (matches shadcn).
- **next-themes** for dark mode (PT players play at night; dark mode is non-negotiable).

**Data layer (the part that actually matters for snappiness)**
- **DuckDB-WASM** in the browser. Loads `projections.json` (or a parquet file) once, then runs SQL queries against 2000+ cards at native speed — filtering, joins, group-bys, percentile ranks. This is what makes the card explorer feel instant even with complex filters.
- **Tanstack Table v8** for virtualized 2000-row tables.
- **Tanstack Query** for any server-state caching.
- **Zustand** for local UI state (selected lineup, filter state). Lightweight, no boilerplate.

**Charts**
- **Recharts** for simple stuff (spider/radar charts for player ratings, bar charts for value).
- **Visx** if you ever want bespoke baseball viz (spray charts, heat maps).

**Persistence (only if you productize)**
- **Vercel Postgres** (Neon under the hood) for users / saved lineups / sync.
- **Drizzle ORM** for type-safe queries.
- **Clerk** or **NextAuth v5** for auth.
- For v1 (personal use), skip all of this — store roster overrides in `localStorage` and load cards from a static JSON in `/public`.

**Pipelines (offline)**
- Python stays where it is — projection engine + future scrapers. Output JSON / parquet to `/public/data/` and Next.js consumes it. You can wire this into a GitHub Action so every push regenerates projections.

## Architecture sketch

```
ootp-pt-optimizer/
├── engine/                # Python — projections, scrapers, calibration
│   ├── projections.py     # ← already built
│   ├── league_baselines.py
│   └── scrapers/          # PT aggregator scrapers (later)
├── app/                   # Next.js 15
│   ├── (dashboard)/
│   │   ├── page.tsx       # Roster + lineup view
│   │   ├── cards/         # Card explorer (DuckDB-backed)
│   │   ├── lineup/        # Optimizer w/ vL/vR splits
│   │   ├── draft/         # Draft engine (live recommender)
│   │   └── tournaments/   # Meta dashboard
│   ├── api/
│   └── components/        # shadcn + custom
├── lib/
│   ├── duckdb.ts          # WASM init, query helpers
│   ├── optimizer.ts       # Lineup search (hill-climb + GA)
│   └── scoring.ts         # WAR-per-PA → runs added by lineup spot
└── public/data/
    ├── projections.json   # Generated by engine/projections.py
    └── meta.parquet       # Tournament aggregator data (later)
```

## Why not the alternatives

- **React + Vite + raw Tailwind:** lighter, but loses Next's RSC, image optim, routing, edge functions, and the one-click Vercel story. If this might productize, Next is the right call.
- **Remix:** great, but Vercel-first DX is weaker than Next's. Don't fight the platform.
- **SvelteKit:** snappier, but the shadcn equivalent (shadcn-svelte) is younger and the data viz ecosystem is React-heavy.
- **Server-rendered table of 2000 rows:** feels sluggish. DuckDB-WASM is the trick that makes filtering "feel like a desktop app."

## What to ship in v1 (1-2 evenings of work)

1. Scaffold Next + shadcn, drop in a dark sidebar layout.
2. Load `projections.json` client-side via DuckDB-WASM.
3. Card explorer page: virtualized table, filter by tier/position/handedness/wOBA threshold, sortable.
4. Card detail page: radar chart of ratings, projected slash line vL/vR, defensive runs by position.
5. Manual roster page: mark which cards are on your active team (localStorage).
6. Lineup view: takes your active roster + opponent SP handedness → returns optimal 9.

Phases 2-4 (draft engine, tournament meta, live stat blending) bolt on after.

## Deploy

```bash
npm i -g vercel
vercel deploy
```

That's it.
